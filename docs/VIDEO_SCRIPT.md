# Сценарій відеозвіту лабораторної 6

## Вступ

«Представляю проєкт SecureSpace — вебзастосунок для безпечного керування
обліковими записами. Сервер написаний на JavaScript для Node.js 24,
дані зберігаються у SQLite. Інтерфейс реалізований засобами HTML, CSS
та JavaScript. Для запуску не потрібні Docker або зовнішня база даних.
У системі є ролі користувача й адміністратора».

## Реєстрація та CAPTCHA

Показати форму реєстрації. Ввести ім’я та email, пароль `weak`, CAPTCHA,
натиснути реєстрацію та продемонструвати відмову політики паролів.
Замінити пароль на `Student2026!Secure`, показати індикатор сили.
Ввести правильні символи CAPTCHA й успішно зареєструвати користувача.

«Пароль повинен мати щонайменше вісім символів, велику й малу літери,
цифру та спеціальний символ. Сервер повторно перевіряє політику,
незалежно від інтерфейсу. Для зберігання використовується scrypt із
випадковою сіллю. CAPTCHA згенерована як PNG, прив’язана до сесії,
одноразова та діє п’ять хвилин».

## Активація

В окремому профілі браузера увійти адміністратором. Відкрити «Листи»,
показати лист із посиланням активації та перейти за ним. Натиснути
«Активувати обліковий запис», показати успішну відповідь.

«У локальній демонстрації використано внутрішню поштову скриньку.
Для справжніх листів передбачений SMTP через TLS. Посилання містить
випадковий одноразовий токен на тридцять хвилин; у таблиці токенів
зберігається лише його хеш».

## Brute Force та адміністратор

Зробити п’ять невдалих входів у користувацькому профілі браузера.
Показати повідомлення про блокування на 15 хвилин. В адміністратора
відкрити список користувачів і журнал входів: email, IP, час, результат,
номери невдалих спроб. Розблокувати користувача. За потреби окремо
показати ручне блокування/розблокування.

«Ліміт прив’язаний до облікового запису, додатково діє обмеження за IP.
Користувач не має доступу до адміністративних API. Блокування одразу
анулює його сесії, а розблокування скидає лічильник спроб».

## Двофакторна автентифікація

Увійти правильним паролем, показати активований профіль, натиснути
«Увімкнути 2FA», ввести код із листа. Показати статус 2FA. Вийти та
повторити вхід: після пароля з’явиться окрема форма OTP. Ввести
правильний код і показати профіль.

«Використано email OTP. Код діє п’ять хвилин, має максимум п’ять
спроб і не може використовуватися повторно. Для вимкнення 2FA
також потрібен окремий код. До другого фактора доступ до профілю
нового входу не надається».

## OpenID Connect

Для автономного відео натиснути «Увійти через тестовий OIDC»,
показати окрему форму провайдера та увійти за його навчальними даними.
Після повернення показати профіль користувача OIDC.

«У цьому записі показаний локальний тестовий провайдер, а не Google.
Виконується справжній Authorization Code flow із PKCE. Клієнт перевіряє
state, nonce, RSA-підпис ID token через JWKS, issuer, audience та строк дії.
Для входу через сторонній сервіс Google реалізований окремий клієнт;
його активація потребує власних Google Client ID та Client Secret.
Без цих реквізитів живий Google-вхід у цьому відео не демонструється».

## Відновлення пароля

Натиснути «Забули пароль?», ввести email. В адміністративній скриньці
відкрити відповідний лист, перейти до форми нового пароля. Встановити
новий пароль. Показати повідомлення про завершення старих сесій.
За бажанням повторно увійти: налаштований 2FA залишається активним.

«Токен відновлення одноразовий і діє п’ятнадцять хвилин.
Запит повертає однакове повідомлення для відомих та невідомих адрес.
Зміна пароля не вимикає другий фактор».

## Підсумок

«Реалізовані всі сім функціональних напрямів і серверний RBAC.
Автоматичні тести перевіряють позитивні та негативні сценарії,
зокрема повторне використання токенів, неправильні OTP, блокування
і перевірку OIDC. SMTP і Google потребують власних зовнішніх налаштувань;
локальні адаптери дозволяють перевірити застосунок автономно.
Додатково реалізовані CSRF-захист, ротація сесій, безпечні HTTP-заголовки
та зашифрована черга листів».
