# SecureSpace — лабораторна робота 6

Готовий вебзастосунок безпечного керування обліковими записами на JavaScript.
Node.js 24+, SQLite, HTML, CSS і браузерний JavaScript. Сторонні npm залежності,
Docker, PostgreSQL, Redis та окремий поштовий сервер для локального запуску не потрібні.

## Запуск у Windows або Ubuntu

1. Установіть **Node.js 24 LTS** або новішу підтримувану версію.
2. Клонуйте з віддаленого репозиторія
3. Виконайте:

```bash
node --version
npm start
```

4. Відкрийте **http://127.0.0.1:3000**.

`npm install` не потрібний: застосунок використовує лише вбудовані модулі Node.js.
Перевірка коду і тести:

```bash
npm run check
npm test
```

Перший запуск автоматично створює `.runtime/lab6.sqlite`, ключ захисту
службових секретів `.runtime/secret.key` та навчального адміністратора:

- **Email:** `admin@lab.test`
- **Пароль:** `Admin2026!StudyOnly`

Ці облікові дані призначені для локальної демонстрації. Сервер за замовчуванням
слухає лише `127.0.0.1`. Звичайні зареєстровані користувачі завжди отримують роль `user`.

Якщо порт зайнятий, змініть `PORT` і `APP_URL` у `.env` узгоджено. Для першого
налаштування скопіюйте `.env.example` у `.env`. У Windows це можна зробити через
Провідник або `copy .env.example .env`; в Ubuntu — `cp .env.example .env`.
Не змінюйте та не видаляйте `secret.key`, якщо хочете зберегти доступ до
зашифрованої черги листів і незавершених OIDC-запитів.

## Що реалізовано

| Вимога | Реалізація |
| --- | --- |
| Реєстрація та пароль | Мінімум 8 символів, великі/малі Unicode-літери, цифра, спецсимвол; перевірка поширених паролів |
| Хешування | scrypt, N=32768, r=8, p=1, випадкова 16-байтова сіль; порівняння через timingSafeEqual |
| CAPTCHA | Згенерований на сервері растровий PNG; відповідь не надходить до браузера; прив’язка до сесії, один раз, 5 хвилин |
| Активація | Лист з випадковим 256-бітовим токеном; у БД лише SHA-256 токена; строк 30 хвилин |
| Захист входу | Після 5 невдалих спроб — блокування на 15 хвилин; лічильник акаунта та обмеження за IP |
| RBAC | Власний профіль для `user`; список акаунтів, журнал та блокування для `admin`; перевірки на сервері |
| 2FA | Email OTP на 6 цифр, 5 хвилин, максимум 5 спроб, захист повторного використання |
| Увімкнення/вимкнення 2FA | Лише з активної сесії та після окремого email OTP; інші сесії завершуються |
| OpenID Connect | Authorization Code + PKCE S256, state, nonce, RS256/JWKS, iss/aud/exp/iat/azp/email_verified |
| Google | Справжній OIDC-клієнт; потрібно вказати власні Google Client ID/Secret |
| Локальна демонстрація OIDC | Окремий тестовий провайдер запускається автоматично, використовує підписаний RSA ID token |
| Відновлення | Одноразовий 256-бітовий токен на 15 хвилин; старі сесії анулюються, 2FA залишається увімкненим |
| Сесії | Випадкові opaque токени, у БД лише хеш; HttpOnly/SameSite=Lax, Secure у production; ротація після входу |
| Захист запитів | CSRF-токен, перевірка Origin, CSP, no-referrer, nosniff, заборона iframe |

## Як показати всі завдання

Відкрийте застосунок у **двох окремих профілях браузера**: користувач у звичайному
вікні, адміністратор — в іншому браузері або приватному вікні. Звичайні вкладки
одного профілю мають спільну cookie сесії.

1. Перейдіть до реєстрації. Введіть слабкий пароль `weak` — сервер покаже порушені правила.
2. Введіть сильний пароль, наприклад `Student2026!Secure`, та символи CAPTCHA.
3. У вікні адміністратора відкрийте **Листи**. Це локальна демонстраційна пошта.
   Відкрийте посилання активації у вікні користувача і підтвердьте активацію.
4. Зробіть 5 невдалих входів у користувацькому вікні. Адміністратор побачить події
   в **Журналі входів**, а у **Користувачах** зможе розблокувати акаунт.
5. Увійдіть користувачем і натисніть **Увімкнути 2FA**. Прочитайте код у листі,
   підтвердьте. Після виходу наступний вхід вимагатиме пароль і новий email OTP.
6. На сторінці входу натисніть **Увійти через тестовий OIDC**. Провайдер має власну
   форму входу: `oidc.user@provider.test` / `Provider2026!StudyOnly`.
   Це тестовий провайдер, а не Google. Для входу Google дивіться розділ нижче.
7. Натисніть **Забули пароль?**, вкажіть email, відкрийте лист, перейдіть за посиланням
   і встановіть новий пароль. Після зміни потрібно увійти знову; налаштований 2FA не скидається.

Жодні кнопки не імітують успішну перевірку: операції виконуються сервером і
зберігаються у SQLite. Лише доставка в локальну поштову скриньку й навчальний
OIDC-провайдер спеціально призначені для автономного показу без зовнішніх облікових даних.

## Реальні листи через SMTP

У `.env` укажіть параметри поштового сервера:

```dotenv
MAIL_TRANSPORT=smtp
MAIL_FROM=Security Lab <no-reply@your-domain.com>
SMTP_HOST=smtp.your-provider.com
SMTP_PORT=465
SMTP_SECURITY=tls
SMTP_USER=your-user
SMTP_PASSWORD=your-app-password
```

Для порту 587 використовуйте `SMTP_SECURITY=starttls`. TLS сертифікат сервера
перевіряється; вимкнення перевірки не передбачено. Сервер повинен підтримувати
AUTH PLAIN після встановлення TLS, якщо вказано `SMTP_USER`.
API додає лист до зашифрованої черги; фоновий обробник доставляє його та повторює
тимчасово невдалі відправлення до 6 спроб. Після доставки текст із черги видаляється.
Локальний розділ **Листи** працює лише з `MAIL_TRANSPORT=outbox` у demo-режимі.
Справжня SMTP-доставка потребує ваших реквізитів; у комплекті їх немає.

## Вхід Google через OpenID Connect

1. У Google Cloud Console створіть OAuth client типу **Web application**.
2. Налаштуйте OAuth consent screen; у Testing додайте свою адресу до test users.
3. Додайте точний Authorized redirect URI:

```text
http://127.0.0.1:3000/auth/oidc/callback/google
```

4. У `.env` задайте:

```dotenv
GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=your-client-secret
```

5. Перезапустіть сервер. Кнопка Google стане активною.

У бойовому середовищі redirect URI має відповідати вашому HTTPS `APP_URL`.
Тестовий OIDC перевірено автоматично повним HTTP-обміном; живий Google-вхід
потребує вашого OAuth-клієнта й не видається за виконаний без цих налаштувань.
Не використовується автоматичне злиття акаунтів за однаковим email:
зовнішня ідентичність прив’язується за парою `issuer + sub`.

## Структура

```text
src/config.mjs          середовище та перевірка конфігурації
src/database.mjs        схема SQLite, запити й транзакції
src/security.mjs        паролі, токени, HMAC, AES-GCM
src/captcha.mjs         PNG CAPTCHA та її життєвий цикл
src/mailer.mjs          локальна пошта, TLS SMTP, зашифрована черга
src/oidc.mjs            OIDC-клієнт та перевірка ID token
src/demo-provider.mjs   окремий навчальний OIDC-провайдер
src/app.mjs             HTTP API, сесії, RBAC та сценарії автентифікації
src/server.mjs          запуск і коректне завершення
public/                інтерфейс без зовнішніх CDN
tests/                 модульні та інтеграційні тести
docs/                  API та сценарій відеозвіту
```

## Межі навчального проєкту

Це навчальна реалізація з конкретними перевірками безпеки, а не сертифікований
продукт. Власна CAPTCHA має обмежену стійкість до сучасного OCR і служить
додатковим бар’єром разом із лімітами запитів. Email OTP залежить від захищеності
поштової скриньки й не є phishing-resistant фактором.

Для публічного розгортання: `NODE_ENV=production`, `DEMO_MODE=false`, HTTPS,
власний `ADMIN_PASSWORD` першого запуску, налаштовані SMTP та Google OIDC,
захищений reverse proxy, резервні копії SQLite разом із `secret.key` та
керування секретами. Застосунок не довіряє `X-Forwarded-For`; за proxy IP у журналі
буде IP proxy, доки окремо не реалізовано довірену конфігурацію проксі.
Зміна `ADMIN_PASSWORD` у `.env` після створення БД не змінює наявний пароль.

Офіційні джерела: Node.js Crypto https://nodejs.org/api/crypto.html ;
Google OIDC https://developers.google.com/identity/openid-connect/openid-connect ;
OWASP Authentication https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html ;
OWASP Forgot Password https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html .
